# 真实 embedding 与 rerank 对比（2026-10-21）

## 配置与方法

真实调用硅基流动 `Qwen/Qwen3-Embedding-8B`（实测4096维）和 `Qwen/Qwen3-Reranker-8B`。生成答案固定使用既有 `kimi-coding/k3` 配置。未使用新提供的火山方舟 Coding 凭证。

沿用16道问题、7份虚构原文，增加30条固定行政干扰记录，共37条。每组取前5条证据，分别运行 BM25、纯向量、RRF 混合、混合加重排。为隔离检索效果，不加入事项状态表、agent工具补查和历史会话；回答模型只看到问题与当前证据，不接触标准答案。问题来源是原始验收集，但语料由 wiki 综合页改成原始记录，因此不能与原工作台问答正确率直接作因果比较。

凭证只存于本机忽略文件，权限0600，已检查跟踪文件和报告未包含该凭证。

## 可观察到的差异

- “英文别名”：BM25 没有召回英文材料，向量将其排到第一，恢复 Seagull 的依据。
- “试点人数”：纯向量找到英文的23名参与者；RRF混合被行政干扰挤出前5，加重排后英文材料升到第一。
- “准备花多少钱”：BM25无证据，向量可以从后续批准变更中找到37万元；重排又将原立项材料升到第一。
- “负责人是谁”：BM25首位命中立项，但向量、混合和重排均受到重复行政材料干扰。重排后前5条都是“行政组”，未找到预期的项目负责人林岚。该裸问句存在对象歧义，说明需要项目/实体上下文，不能仅依赖相关性排序。30条相似干扰材料也放大了这个退步，不能把它当成所有真实企业数据的自然分布。

## 运行状态与限制

应用5181已启用真实 BM25 + 向量 + RRF + rerank。浏览器用口语问题“之前卡着的那件事后来搞定了吗，谁在跟？”验证：识别支付联调已完成、小王跟进，引用前后记录，页面显示真实检索链路。

冷启动会生成37条记录和16道问题的向量，后续复用缓存。本轮缓存命中差异明显，耗时不能作为公平的线上性能比较。未做多轮稳定性、批量生产负载或其他模型的横向评估。

首轮建议保留混合加重排，同时优先补项目实体路由、重复证据去重和歧义处理；不建议把向量或rerank当成当前状态判断与实体消歧的替代。
