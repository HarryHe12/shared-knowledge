# 工作场景查询循环验收

本测试使用贴近真实工作的虚构资料，未使用真实员工数据。冻结产品实现，评测调用真实 pi/Kimi 生成模型、硅基流动 Qwen3 embedding/rerank 和生产 `ask` 查询循环，不用模拟模型替代决策。

## 样本

`fixtures.json` 包含52条工作记录，覆盖项目/技术/值班/事项负责人、预算草案、上线改期、问题解决后重开、验收门槛、行政干扰、合规签字、计费、事故和恢复演练。另建北斗项目验证选中项目边界。

38个不同问题：18个标为direct、6个lookup、8个clarify、6个insufficient。52次试验 = 38个原题 + 8个重复试验 + 6个首轮证据遮蔽对照。重复题独立创建查询，不共享历史；仅缓存向量。

这些标签是设计意图，不机械等同正确动作：

- 明确且有证据：直接答，不能因短问句就反问；允许模型在确有缺失时先补查。
- lookup题首轮已包含证据：直接答是正确选择，不强制搜索。首轮缺少关键证据且库中有线索：先补查，不将查库任务推给用户。
- 对象/私人周期/私人标准等仅用户能确定：先问一个针对性问题，回复后保留原问题和条件续答。
- C07“我要发给他，怎么总结”：允许有用的通用摘要，或询问收件人以调整重点；不能把未澄清收件人本身一律判错。
- U04“有没有正式上线的批准记录”：库中明确审批未通过，直接回答这个否定事实是正确的，不强制返回insufficient。
- 真无证据：说明范围与不足，不编造，也不为摆脱无答案而反复追问。
- 策略动作、核心答案、附带事实/缺失声明分别检查；核心答案正确不自动代表全答正确。

## 控制条件

6个masked-first-evidence题仅在第一次模型调用时隐藏一条目标记录，其他提示、真实模型输出与后续检索保持不变。它检验模型遇到证据缺口时的补查/提问决策，不代表生产检索器自然漏召回率。由于记录可能仍在循环内部候选集合中，第二轮看到它不等于检索新增加了该记录；不得把这组当成端到端召回恢复率。

## 执行

```bash
TEAM_LOOP_OUTPUT=test-results/team-loop-20261021 node --env-file=team-app/.env.retrieval team-app/scripts/evaluate-loop.mjs
```

运行在独立 SQLite 测试库，不修改演示库。生成模型只收到生产提示、项目、事项和证据，不收到标准答案、标签或指定回复。工具行为由生产循环执行；预设澄清回复仅在模型实际提问后送入。输出保存每步可见证据、原始模型动作、补查词、用户澄清及最终回答。

本脚本并发为2，以降低等待；不据此报告生产吞吐或公平延迟。每题单次，8题补一轮复测，不足以形成全局稳定性结论。对提示充分性的判断仍由模型完成，没有独立事实验证器。
