# 企业微信与 Agent 接入

本目录是统一知识服务的接入层。公司权限、原始记录、聊天和问答由 `team-app` 处理，采集端不使用一个共享业务账号代表所有员工。所有入口仅供内部员工。

此分支包含新的权限与可靠队列实现，部署后才生效，不能据此认定现有线上服务已经升级。需要 Node >=22.19。

## 消息处理

1. 企业微信回调验签、解密、核对企业与应用。
2. 按 MsgId 写入本地 SQLite 收件箱后才返回接收回执；回执不代表已入库。
3. 工作进程用独立桥接密钥，按已验签的 FromUserName 换取绑定员工短期会话。
4. 查询员工当前范围，通过统一 `/api/v1/conversations` 和消息接口保存或问答。原文作者是真实员工 ID。
5. 推送前重新检查权限，成功后清除队列正文与答复。失败有退避重试和上限，重启可继续处理，重复回调不重复写入。

同一员工的消息按顺序处理。选择的范围和聊天请求在发给内核前持久固定，重试不会把记录挪到另一个范围。员工身份重新绑定后旧会话失效，旧身份消息不能在新身份下恢复。

企业微信发送答复与本地确认无法做到分布式原子提交；进程恰在推送成功、登记确认前退出时，答复可能重复，知识记录仍由内核幂等去重。权限撤销不能追回已经发到员工微信的消息。

## 初次部署

先按 [知识服务说明](../team-app/README.md) 配置管理员、公司、品牌、门店和员工岗位。生产不能使用 `TEAM_LOCAL_VALIDATION=1`。

在 `/organization` 登记 `wecom` 应用，设置公司/品牌上限。设置 `secret_env` 为服务端桥接密钥的环境变量名称，例如 `WECOM_KB_BRIDGE_SECRET`。在内核环境配置对应的随机密钥，至少 24 字符；启用应用并人工核实绑定每个企业微信 UserID 与员工账号。

采集服务配置见 [.env.example](.env.example)，仅示例变量，没有可用凭据：

```bash
# 从仓库根目录运行；实际凭据放服务器权限受控的 env 文件。
node --env-file=kb-system/.env kb-system/collector/src/server.mjs
```

内核和采集端的桥接密钥值必须一致，分别使用核心登记的环境变量名和采集端 `KB_CHANNEL_BRIDGE_KEY`。`KB_CHANNEL_APP_ID` 是知识库内登记的应用 ID，不是企业微信 AgentID。采集默认只监听本机 9100，公开路径为 HTTPS `/wecom/callback`，由反向代理转发。不要公开内部端口或数据库文件。

企业微信的五项配置必填；不再使用开发默认 Token/AESKey。未配置身份桥接、推送凭据或员工绑定时明确拒绝，不回退到匿名/共享账号。旧模拟器默认值不能直接用于生产；回调协议和离线演练可参考 `collector/test` 的加密回调测试。

升级前同时备份内核数据库、采集收件箱及环境配置。已有 systemd/pm2 需要显式加载新环境变量、确保数据目录可写并重启，不要只看进程 active 就认定业务可用。

## 员工使用

- `帮助`：查看使用方法。
- `范围`：列出当前获准知识范围。
- `/范围 完整编号或名称`：选择一个范围。
- `/范围 全部`：恢复本公司获准范围内汇总查询，最多 40 个。
- `记录：一店冷柜已修复`：明确保存；有多个保存目标时会提示先选择一个，再重发原文。
- `问：冷柜维修到什么程度了？`：提问，不保存为工作事实。
- 普通口语消息由内核辨别意图；含糊时澄清，不冒充成功保存。

文字和已转写语音可处理；图片、附件或未转写语音会明确提示尚未入库，尚无 OCR/附件库。撤回和更正使用已登录的电脑客户端，携带记录 ID 和当前 version。

个人微信需通过企业微信官方微信插件等已部署入口进入，同样保留企业微信身份；没有实现个人微信非官方机器人。当前按应用私聊设计，群聊接收和复杂消息类型未验收。

## 电脑 Agent 兼容入口

推荐直接用知识服务 Skill/SDK。保留的 `/agent/ping`、`/agent/feed`、`/agent/ask`、`/agent/search` 也必须带员工 `Authorization: Bearer ...`，业务请求还需 `X-Knowledge-Scope`。

`/agent/feed` 需要稳定的正文 `idempotency` 或 `Idempotency-Key`，重试复用。`AGENT_API_KEYS=name:key,...` 如配置，只通过 `X-Agent-Key` 额外保护网关；它不能代替员工会话，旧应用密钥放在 Bearer 中不会成为员工身份。旧调用方需要迁移，不应为兼容恢复共享账号。

## 旧 Wiki 和每日摘要

旧 librarian 平面 Wiki 编译与静态名单推送默认停用，即使显式设置 `KB_ENABLE_LEGACY_EXPORT=1`，也拒绝组织管理的公司范围，避免把权限不同的资料写进统一目录或推送给无权员工。

仅原有未绑定公司的私人范围可显式使用旧导出，必须提供获准身份 `KB_SERVICE_TOKEN` 和 `KB_SERVICE_SCOPE`。这些不是平台万能账号，也不授予超出账号的权限。旧编译器的计数游标、覆盖与删除依赖没有重写，不能作为受控公司知识事实来源。历史 Wiki 文件需另行限制访问，正式系统不向聊天检索导入这些文件。

## 验证

在仓库根目录运行 `npm test`。采集离线测试覆盖真实加密回调、接收后持久化、权限检查、选范围、丢响应重试、租约接管、重试上限及 Agent 员工身份；不会访问真实微信。上线还需用两个不同门店账号检查绑定、推送、跨店拒绝、退出/停用、模型质量和恢复流程。
