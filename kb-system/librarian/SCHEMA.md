# Wiki 编译规则（SCHEMA）

> 本文件是知识库"图书管理员"层的管理灵魂。Wiki 不是数据库，是 AI 编译出来的**活页笔记本**：它从不可变的原始记录中提炼知识，逐条溯源，随时可整页重建。
>
> 理念来源：Karpathy 的 LLM Wiki——原始记录是唯一事实来源，Wiki 只是它的一份带引用的、会不断重写的"编译产物"。

## 一、铁律（任何页面、任何时候都不得违反）

1. **原始记录是唯一事实来源。** 知识内核（team-app）里的记录不可变、可溯源；Wiki 里的每个字都只是记录的整理，不是新事实。Wiki 丢了可以整站重建，记录丢了一切归零。
2. **每条陈述必须带引用。** Wiki 中任何事实性陈述，句尾必须跟一个 `[^短ID]` 脚注引用（短 ID = 记录 id 前 8 位），页面末尾的"引用清单"给出短 ID → 记录原文摘要的对照。没有来源的话不许写进 Wiki。
3. **矛盾要标注，不要覆盖。** 新旧记录说法冲突时，两个说法都保留，用 `⚠️ 矛盾` 标注，并分别给出引用和时间。让后来的人自己判断；只有新记录明确说"之前说错了"时，才在旧说法旁注明"已被 [^xxxx] 修正"。
4. **区分"成员陈述"与"AI 整理"。** 谁说的就写谁的名字（`@张三：……[^短ID]`）；由 AI 跨记录归纳出的结论，必须标明"（整理自多条记录）"，并在措辞上保持可核验。AI 不创作事实，只搬运和组织。
5. **Wiki 永不手改，可整页重建。** 人不直接编辑 Wiki 页面；要改就改原始记录（入库新记录、更正、撤回），然后重新编译页面。任何页面在任何时候都可以从记录全量重建——这保证了 Wiki 永远不敢偏离事实太远。

## 二、目录结构

每个知识范围（scope）一棵独立的 Wiki 树，互不混写：

```
wiki/                      # 某 scope 的 Wiki 根目录（多 scope 时每个 scope 一份，见"权限注意"）
├── index.md               # 全站索引：所有页面的清单 + 一句话定位 + 最后更新时间
├── .cursor                # 编译游标（纯数字：已编译到的记录条数），非 Wiki 内容
├── projects/              # 项目页：按正在推进的项目/事项组织，一个项目一页
│   └── <项目名>.md
├── entities/              # 实体页：人、客户、系统、供应商等，一个实体一页
│   └── <实体名>.md
├── topics/                # 主题页：跨项目的知识主题；拿不准归类的进 topics/杂项.md
│   └── <主题名>.md
└── digests/               # 每日摘要（digest.mjs 生成），文件名即日期
    └── 2026-10-21.md
```

页面命名：用记录里最常用的称呼，短、稳定、不带日期。重命名时同步更新 index.md 与所有指向它的 `[[链接]]`。

## 三、页面统一模板

每页结构如下（无内容的章节可整节省略，但顺序不变）：

```markdown
# <页面名>

> 一句话定位：这页讲的是什么。

**状态**：进行中 / 已完结 / 搁置 ｜ **最后更新**：YYYY-MM-DD ｜ **来源**：N 条记录

## 当前状态
一句话说清现在到哪一步了，带最新引用 [^短ID]。

## 关键事实
- 事实一（谁说的、什么时候）[^短ID]
- 事实二 [^短ID]
- ⚠️ 矛盾：@张三 10-12 说 A 方案已确定 [^a1b2c3d4]；@李四 10-18 说仍在评审 [^e5f6a7b8]

## 待办与阻塞
- [ ] 待办事项 [^短ID]
- [x] 已完成事项 [^短ID]

## 时间线
- YYYY-MM-DD @作者：发生了什么 [^短ID]

## 引用清单
- [^a1b2c3d4] YYYY-MM-DD @作者：记录原文摘要（一两行）
- [^e5f6a7b8] ……
```

要点：

- **一句话定位**让搜索引擎和人都能在 5 秒内判断这页有没有用。
- **状态行**是 lint 巡检的重点对象：与内核 `state()` 投影不一致的"当前状态"会被标为过时。
- **引用清单**是页面与原始记录之间的桥：每个脚注都能还原出原文。清单条目超过 30 条时，只保留仍被正文引用的，旧的随正文一起归档进"时间线"。

## 四、增量编译策略

1. **游标推进。** `wiki/.cursor` 保存已编译的记录条数。每次编译只处理游标之后的新增记录；编译成功后推进游标。LLM 调用失败时不推进，下次重试；LLM 未配置时照常推进（记录已在内核里，问答检索不受影响，只是暂时没人整理）。
2. **归属判断。** 每条新记录先判断归属：属于某个项目 → projects/；在描述某个实体 → entities/；通用知识、跨项目主题、暂时拿不准的 → topics/（拿不准的一律进 `topics/杂项.md`，宁可堆积不可乱建页）。一条记录可以喂给多个页面。
3. **追加优于重写。** 增量编译时优先往现有页面的"时间线"追加、更新"当前状态"，而不是整页重排；整页重排留给人工触发的全量重建。
4. **页面规模控制。** 单页正文超过约 200 行时，把旧时间线折叠为"YYYY 年 Q 季度"小结（小结同样要带引用），或按子主题拆页并在原页留 `[[链接]]`。
5. **跨页链接。** 页面之间用 `[[页面名]]` 互链（如 `[[订单系统改造]]`、`[[张三]]`）。链接目标必须存在（lint 会查断链）；新建页面时顺手更新 index.md 和提到它的旧页面。
6. **index.md 同步。** 每次编译新增/删除/重命名页面后，必须同步更新 index.md；index.md 是全站唯一权威目录，lint 会拿它查孤儿页。

## 五、权限注意（多 scope）

- 知识内核按 scope 隔离授权，**Wiki 目录也必须一一对应**：每个 scope 一份独立 Wiki 树（如 `wiki/<scope-id>/`），绝不跨 scope 合并编译、绝不把 A 范围的引用写进 B 范围的页面。
- 当前单机开发只有一个默认库，直接用 `wiki/` 根目录；接入多 scope 后，compile/digest 需逐个 scope 运行，输出到各自目录。
- Wiki 文件的阅读权限不得低于其来源记录的 scope 权限——谁看不到原始记录，谁也不该看到编译出的页面。

## 六、重建原则

任何页面（包括 index.md）都可以随时全量重建：清空 Wiki → 游标归零 → 按时间顺序重放全部记录重新编译。重建不改变任何原始记录，因此它是安全的、可随时执行的"后悔药"。增量编译只是省 token 的优化，正确性永远以"能整站重建"为底线。
